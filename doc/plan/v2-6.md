# V2-6：在五条本机 JIT 路线上接回完整作者程序

交付对象是用户安装后调用的 IntentDSL。V2-5 的五个出口已经有行程序路线。替换 V1 还需要完整的语言、程序调用和数值覆盖，以及在可比硬件上保持成熟路径的性能。沿用[编译树与出口合同](../architecture.md)、[作者语义](../design/kir.md)、[CPU](../design/cpu.md)、[Block](../design/block.md) 和 [DSA](../design/dsa.md)。

## 1. 工作集与顺序

启动每个工作包前用 Bench 的 `list`、`describe` 确认作者符号、显式 kernel 序列、输入、dtype、容差、oracle 和同设备对照。当前 Bench 登记有 372 个工作负载，其中 30 个 `program/`、309 个 `corpus/`，另外 33 个为独立算子、advanced 或硬件专项入口。一份程序可以被多个入口引用。由产品维护唯一算法源码，Bench 持有输入、成熟实现和测量协议。

下表按依赖推进。每行的程序名均指 `program/<name>`，合计 30 个。右列是验证同一组件的其他作者程序。若已有登记没有匹配硬件实测对照，可做数值验证，保留性能待测状态。

| 顺序 | 产品程序与本组完成条件 | Catalog 中的迁移或迁移后复用检查 |
|---|---|---|
| 1　索引、逐元素与状态写回 | `relu, swiglu, rope, transpose, dropout, adamw`。符号域、broadcast、绝对成员坐标、view 局部下标、stride、掩码 fill、整数混合、InOut 和多输出贯通五个出口。首次调优逐试跑恢复整个可写 allocation，连同读别名一起重绑；验证重叠 view、初始 InOut 和 tail 写入 | `corpus/mojo/rotary_embedding_equivalent_index`，`corpus/mojo/dropout_residual_rms_norm` 的索引与状态部分 |
| 2　归约、归一化与阶段调用 | `softmax, layer_norm, batch_norm, group_norm_backward`。数值状态元组、Welford、标量广播、生效的累加 dtype；捕获静态 program 调用拓扑、受形状支配的 workspace、fill、多个输出和完成点 | `weighted_rms_norm`，`corpus/triton/fused_add_rms_norm`，`corpus/mojo/layer_norm_backward` |
| 3　前缀、分段、不规则访存 | `cumsum, embedding, csr_spmv, jagged_mean, nonzero, histogram, moe_alignment`。显式索引、可选映射、ragged offset、scan carry、scatter/atomic 与按键合并。本组实现有序循环，CSR 在每行按非零项的原顺序严格标量累加。两阶段直方图和 MoE 的 count、prefix、scatter、mark 四阶段全部按作者顺序计时 | `corpus/triton/flaggems_histogram`，`cpu/histogram`，复用上一组的 workspace 与多次调用 |
| 4　稠密与量化收缩 | `gemm, batched_gemm, ragged_gemm, int8_gemm, q4_projection, fp8_gemm`。先做标准收缩/尾块/epilogue，再沿 batch/ragged 分组，最后加入原生整数累加、Q4_K/Q8_K 记录与分组 FP8 缩放 | `corpus/triton/moe_expert_projection`，`corpus/weft/q4_k_projection`，`corpus/mojo/qkv_projection` |
| 5　有序状态、窗口及依赖 | `gated_delta, causal_convolution, cholesky, mamba_chunk_state, causal_linear_attention`。保留 ordered 递推与阶段读写；region_fold/scan 的可切分 source 与只读 capture 具有不同角色。mamba_chunk_state 按独立 chunk 并行做 BF16 收缩和 FP32 累加，复用第 4 组；跨 chunk 递推的证据另取 gated_delta 或 causal_linear_attention | `corpus/mojo/selective_state_scan` 及 causal/scan 同类登记；检查空域、初值、最后一步状态 |
| 6　混合计算 | `attention, paged_decode`。联合策略组合收缩、归约、间接页访问和状态保留，提交一个相容的拓扑及行组。分页 partial 和 merge 仍是作者声明的独立调用 | `corpus/triton/flash_attention_backward`，`corpus/mojo/paged_mla_decode_partials`，`corpus/cutile/grouped_flash_decode` |

第 6 组的 backward 登记项沿用 V1 同名 Triton 用例的 Q/K/V 输入 `[2,16,2048,128]`、`HEAD_GROUP=1`；GQA 前向和分页 decode 在本组覆盖，多个 query head 向同一 dK/dV 的累加属于另一项 `corpus/mojo/attention_backward`（HQ=8、HK=2），不计入本组反向覆盖。

先做读写、stride 和 effects，后三组才能复用同一份 alias 和有效域知识。尽早交付 program 是为了在归约反向与路由中立即检验其输入恢复、workspace 寿命和原生计时。收缩先于混合区域，独立验证局部实现后再加入联合决策。首批不需要额外的物理节点。

## 2. 组件落点

缩写 K、B、C、D 分别表示 `levels/algorithm/kir`、`levels/execution/block`、`levels/execution/cpu`、`levels/storage/dsa`。T、CT、W、M、BC 对应 `exits/{triton,cutile,weft,mojo,bangc}`。每次扩展从真实作者语义贯通到可执行产物。终验应能从中间表示指出归属、数值规则、程序如何获得数据以及最后一个使用者。

| 组 | 前端、K 与模型内组件 | 出口 legalize 与 DSA 局部实现 |
|---|---|---|
| 1 | `frontend/python` 捕获纯函数、索引/整数运算与形状；K 类型、promotion、view、读写 effects；B 做实例覆盖、轴映射与向量/标量尾部；C 依据写集合隔离任务；D 形成有界、跨距搬运 | T 的坐标/mask、CT 的矩形 tile 或间接 gather；W 保留结构化访问，M 形成等价 SIMD 和尾段，BC 选连续/跨距供数和逐元素微核 |
| 2 | K 的 reduce/tuple 有 identity、空域与数值许可；B 的驻留或流式和 C 的行间分工消费同一合同；D 规划输入/增益/统计的复用、累加器与完成点。`frontend/python` 捕获静态 program，`runtime/kir` 管绑定、alias 组、workspace 所有权和试跑恢复；各出口执行既定调用 | T、CT 将摘要兑现为本地 collective；W 发 task 及唯一 host/join，M 降低循环、向量摘要；BC 扩展求和、极值、元组摘要及等价尾部微核。CPU 导出完整原生序列，GPU/MLU 使用同流/队列 |
| 3 | K 验证 gather/scatter 边界、atomic order/failure order、旧值、键域和空 bin。B/C 分别决定片段或任务成员覆盖，scan 段内状态与段间 combine；D 对冲突、依赖、私有累积及已有合并阶段作供数决定 | T、CT 选有效的原子/间接访问；W、M 保留合法次序，选择原生或合法的任务局部实现；BC 添加间接装载、局部 collective 与目标原子，拒绝目标无法满足的顺序 |
| 4 | K 定义 contraction、数值和解码步骤；B/C 查询出口的 tile、输入表示和 packing 需求，选择完整行。C 明确共享准备与 join，D 按行检查矩阵/向量引擎可达性、双侧供数及重叠存活 | T 映射 dot，CT 映射 tile MMA；W 使用已声明的 RVV/矩阵实现，M 在出口兑现 SIMD 或矩阵实现；BC 选择矩阵块、权重空间、packing/解码微核。BF16 不引入隐式 FTZ；不同指令合同分开说明 |
| 5 | K 的有序 region、状态 captures 和循环携带值可验证；B 形成实例内遍历，C 保持 task 内顺序或显式 join；D 确定状态 owner、迭代间依赖与私有窗口寿命 | T/CT 生成携带状态的循环；W/M 分开向量化独立成员与顺序成员；BC 组合窗口搬运、更新微核和等待。跨步重结合只在作者原语明确许可时启用 |
| 6 | B/C 在同一计算区域复用上述分析，控制、供数和联合参数行共同验证；D 为实际访问选择 supply，一行改变拓扑即剔除并记录。K 的空 split、NaN 和 merge 行为来自作者 | T、CT、W、M、BC 各自接管已兑现的访问、矩阵/向量计算与状态；serializer 只输出这些结构。复测整个 attention/paged program，包括写回和必要 workspace |

每个主要优化至少用开发程序与另一个作者程序检验适用性或受益。候选替换走 `derive → compile/explain → compare → measure → adopt/discard`，数值许可独立于性能选项。若能力缺失需要变更树、职责或产品目录，单独说明缺口并交由设计裁决。性能轮只改相应分析、策略、实现、经验行和必要的目标合法化。

**开发期口径（第 2 组起）。** 每个程序在适用设备和出口做一次 Bench 完整调用，核对数值，查看与同设备 V1、成熟实现的用时差。约两倍以上的差距优先定位到编译单元，较小的差距列入 V2-6.P。结构仍由代价模型选择；若模型选错且原因明确，就修对应代价项。开发期采用单轮读数，不要求逐项 P1、留出集冻结或准确度计分。原生编译代价异常由所属出口约束候选。发行前的性能收口集中复测长尾与成熟实现，保留数值合同和完整调用口径。

### V2-6.P 待办（第 2、3 组）

第 3 组开始时重测了三个长尾。MLU370 BF16 Fused Add RMSNorm 从 407.958 ms 降至 2.302 ms（V1 2.190 ms）。x86 Mojo GroupNorm backward 从 48.106 ms 降至 1.786 ms（V1 1.072 ms）。H100 cuTile GroupNorm backward 从 2.295 ms 降至 0.175 ms（同设备原生库 0.095 ms）。下方第 2 组表保留当时的读数。后两项的剩余差距分别归 CPU 的投影访存与 cuTile 的并行划分。

| 优先级 | 现象 | 负责单元和下一步 |
|---|---|---|
| 高 | GroupNorm backward 的 RVV、x86 Weft 与 GPU 其余路线 | CPU 的任务及向量供数、Block 的多归约遍历。分别检查输入梯度和仿射梯度成员的访存、并行度及重复归约。x86 Mojo 与 H100 cuTile 的本轮读数见上。 |

| 高 | x86 Mojo 的 BatchNorm、Dropout Residual RMSNorm；RVV 的部分反向程序；GPU LayerNorm backward | CPU/Mojo 的元组归约及随机数向量实现、Weft 的 BF16 运算、Block 的分桶与多归约供数。分开看计算、共享读取和 partial 写回。 |

### 第 3 组开发读数与性能收口项

V2-6.P 已在产品树之外建立扩展包试验原生 Tile IR 13.3 的实例内计数原语（`cuda_tile.alloca` + `MemoryScope.BLOCK` 原子加），经 `derive → explain → measure` 实测：`tileiras 1.6` 将 `alloca` 指针降低为全局暂存区描述符与全局原子（`REDG.E.ADD.STRONG.SM`），5090D 完整调用耗时 1840.7 µs；分块两半字节 `16×16` INT8 MMA 候选数值精确但耗时 241.7 µs，均慢于当前 CTA 独占 partial 行的 90.1 µs，故按规则丢弃，不扩展 `@ct.kernel` 交付合同。

AMX BF16 会将输入、累加中间值及抵消产生的次正规数冲零，默认严格合同保持 FP32 展宽不变，仅在作者显式声明 `allow_subnormal_ftz=True` 时才允许选用 `onednn-brgemm-bf16` 并与 ATen 的 FTZ AMX 对照。

SG2044 和 RVV V100 的完整 FP16 QKV 在本轮登记的单核运行环境约为 49 秒和 38 秒，routed expert 约为 80 秒和 71 秒。保留该设备上的原始用例。对应大形状尚缺同设备成熟实现的完整计时，继续由 Weft 评估宽度转换与右面板供数。MLU 的 Torch INT8 调用会转到 CPU，该环境在 Bench 中标记为缺少设备实现。

x86 系列测量有毫秒级异常读数。相同 Mojo 结构的 BF16 batched 在配对测量中为 106 µs，单实现进程中有一次为 1.68 ms。连续测三个程序时，dense 与 INT8 分别出现过 3.61 ms 和 10.58 ms，另起进程测得 53 µs 和 28 µs。设备数值检查均通过。已观察到局部 CPU 繁忙，调度与线程运行时分别占多少尚未确定，性能收口时用相同核集定位。

## 4. 发行包与从安装使用

1. 在产品 `cmake/` 与根打包入口从已安装的 CompilerInfra SDK 构建。sdist 包含完整手写源、TableGen 输入、构建清单及 agent 资产；在干净构建环境从 sdist 重新构建 wheel。发行包收齐产品共享库、对应框架 Python 绑定或精确依赖、已安装前端、各 runtime、30 个 program 与 ABI。检查本地 paths、动态库查找和第三方分发许可。
2. 产出 x86_64 和 riscv64 的原生 wheel。MLU 主机使用匹配系统 ABI 的 wheel；CNCC、CNRT、CNNL 和设备驱动记录为外部依赖。RISC-V 在原生机器验证 Triton–Weft、ISA/VLEN 与实际 CPU 集。同一进程可用的 Triton 发行组合按实际结果说明。从 wheel 安装使用无需 LLVM 开发 SDK，从 sdist 构建说明列出 SDK 和工具链版本。
3. 按声明的 manylinux/glibc 下限核对 wheel 标签、依赖符号版本及最老支持环境中的真实安装；原生 Linux 包与 manylinux 包分别验证。在源码树外创建新环境，清除开发 `PYTHONPATH` 和产品库覆盖，分别安装 wheel 和从 sdist 构建的 wheel。运行安装包的 setup/doctor 解析实际工具链、缺失依赖及设备；断开网络后从安装包查询双语手册。验证导入位置、`layout`、五个显式后端的普通 JIT、冷/热调用、换 buffer、错误设备和缺工具链诊断。检查从安装清单发现的 skill 与前端绑定，以及 CLI/MCP 对同一候选的 `inspect / derive / explain / measure`。`compilerinfra-dev host-config` 为 Codex/Claude 提供同一动作目录；将可复制命令写进双语手册。
4. `doc/` 集中中英文安装、作者语言、模型接入和组件指南，示范在已存在的节点或出口增加策略/微核，说明源码位置、如何比较父子候选、如何交给独立 Bench。README 只保留安装、首个真实调用、手册和贡献入口。

## 5. 验证安排

日常开发只跑受影响程序、一个独立复用程序及相关数值边界。Bench 负责输入、oracle、同设备基线、计时和输出；agent 使用产品默认入口。完整核查在每组接回后或发行候选上由既有 Bench suite 执行。先按五个出口走完 30 个完整 program，再按登记清单遍历每台环境适用的其他实现和所有已有 cases。验证安装、生成、原生编译、执行、数值、性能各自列出，保留失败和跳过原因。

GPU 使用 5090D 与 H100 的两出口、完整算子图重放；x86 同时运行 Mojo/Weft，SG2044、K3 两类核心和 RVV V100 运行 Weft；MLU370 用 CNRT notifier。K3 须待入口恢复。RVV 缺 oracle 依赖时传实际输入、别名和输出给既有 oracle，性能对照留在本机。CPU 多 kernel 和初始化合并在一个原生区间。全量沿用 Bench 的 latest/daily/experiments，不恢复已暂停的每日任务，不新增平行测试或性能台账。最终逐项说明有无相同语义的成熟实现、数值是否通过、长尾由哪个单元负责，以及包能否独立使用。
